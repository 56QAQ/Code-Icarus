# Code:Icarus｜项目总体框架（原始需求）

> 本文件保存项目发起人给出的原始需求，是所有设计决策的最终依据。

## 一、游戏定位

《Code:Icarus》是一款使用 **Godot 引擎开发、3D 方块风格的上帝模拟游戏**。开发、引擎操作、构建与测试原则上全部由 Claude Code 完成，玩家主要负责提出需求和评价实际体验。

核心体验类似 WorldBox：玩家并不直接经营一个国家，而是观察世界中的居民和文明自主发展，并通过管理员能力自由干涉，观察由此产生的后果。

本项目最重要的特色是：

**具有不同源动力与人格的魔法少女，通过不同决策塑造文明；可破坏的物质世界则构成文明发展的真实基础。**

游戏不是预先编写好结局的剧情播放器。战争、繁荣、衰落、迁移和叛乱，应尽量由世界状态、居民行为和统治者决策共同产生。

## 二、世界观与主要角色

游戏发生在未来末日背景下的一片与世隔绝的空岛大陆。人类创造了人造人社会，试图观察不同“源动力”如何引导文明克服困难、走向未来。背景主要服务于玩法，不要求制作剧情演出。

世界中的居民分为两类。

**普通人造人**负责生产、建造、运输、贸易、研究及一般社会活动，具有个人需求、技能、关系和满足度，不是完全服从统治者的单位。

**魔法少女**是拥有源动力与超凡能力的特殊人造人，既是重要战力，也可能成为地方管理者、领域负责人或国家统治者。

魔法少女以“象征某种源动力的魔法少女”作为标题，有自己作为人类的随机名字池，例如“象征美食的魔法少女，弥弥”。国家的显示名称不变，但标题随最高统治者变化，例如“美食的文明，拉米娅”。其源动力可能是正面（‘希望’，‘勇气’，‘光明’，‘美食’）或者负面（‘愤怒’，‘嫉妒’，‘绝望’，‘暴食’）的词汇，每个魔法少女都拥有等级系统，随等级解锁的最多4个和她的源动力相关的超能力魔法，2个主动效果，2个被动效果。总体上来讲，正面魔法少女的数值较低，但倾向于联合和提供更好的治理；负面魔法少女的数值较高，但倾向于用高惩罚来治理国家，并且不太会和其他魔法少女合作治理。

一个国家可以存在多位不同源动力的魔法少女。她们可以合作、竞争、拒绝命令、发动叛乱、夺取统治权或建立新国家。

统一空岛的魔法少女及其源动力获得本轮胜利，但统一不等于文明必然幸福或可持续。游戏可以同时记录人口、生活水平、知识、生态与稳定性，呈现不同的文明结局。

## 三、世界结构：地格与 cube 两个层级

### 地格是世界管理单位，cube 是物质组成单位

世界首先被划分为大量规则地格：水平方向为正方形，必要时在垂直方向继续分层，组成三维区块。

每个地格具有生态群系、地形、环境和归属等信息，内部则由大量 cube 构成。例如，一个深海地格可以标注为“深海生态群系”，其内部主要是数百 × 数百 × 数十个水 cube。

**地格负责生成、存储、加载和模拟调度；cube 负责具体物质、形状、损伤与变化。**

地格边界只是管理边界，不能成为世界中的无形墙。水流、火灾、道路、建筑、居民与战争都应能够跨越边界。

### 世界不需要始终完整加载

采用“按需生成、分级模拟、修改持久保存”的总体思路。

**尚未探索或使用的地格**，可以主要保留生成种子和必要的宏观信息，不必提前实例化内部所有 cube。

**已生成但暂时没有活动的地格**，保存状态后进入休眠，不持续保留完整的渲染、碰撞和逐 cube 模拟。再次激活时，恢复原有世界，而不是重新随机生成。

**有人造人、魔法少女活动，或者正在接受玩家干涉的地格**，优先进行更详细的模拟。但“地格处于活动状态”也不意味着其中每个 cube 都必须逐帧计算，仍然只更新发生变化的部分。

完全均质的水、岩石等区域应允许压缩表示。逻辑上由大量 cube 构成，不意味着内存中必须为每个 cube 创建一个独立对象。

### 休眠不能切断因果关系

无人地格可以休眠，但正在向外蔓延的火灾、洪水、坍塌等，不能仅仅因为无人而立即停止。此时应临时激活相关区域，或者用低成本事件继续传递影响。

需要缓慢演变的休眠区域，可以只保留少量摘要、时间戳和待处理事件，在必要时更新；不要求持续加载完整地格。

**原则是：空闲区域不花费精细模拟成本，正在影响世界的事情不能被无故冻结。**

玩家移动镜头主要改变显示细节，不应凭空改变国家的命运。远处正在活动的文明仍需发展，只是不一定使用与镜头近处相同的表现和计算细节。

玩家与居民造成的采掘、建筑、污染、破坏等变化必须持久保存。不能通过离开再回来，让资源、建筑或灾害恢复初始状态。

## 四、方块世界与物理表现

地形、树木、矿石、水、建筑、角色、武器和装备，都以 cube 为基本组成与可修改单位。

目标是具有类似“3D Noita”的物质交互感：挖掘会留下实际缺口，火焰会作用于材料，水能够流动，结构失去支撑会坍塌，陨石会真实改变地形和建筑。

但这不意味着每个 cube 都是一个独立刚体，也不要求完整现实物理。应通过分块网格、材料规则、局部更新、结构支撑和聚合碎片实现一致、可理解的效果。

角色由具有局部体素结构的身体部位组成。损伤应实际影响身体和功能，例如手部损坏导致无法持握、腿部受损影响移动、连接断裂造成断肢。装备和武器同样参与物质交互。

修复与再生必须有明确条件和资源成本，不能通过再生无限复制材料或个体。

**优先保证交互真实、一致且能影响玩法，再逐步提高精度和规模。** 体素尺寸、地格大小和物理活动范围，应通过原型测试确定，不提前承诺未经验证的极端规模。

## 五、两类 AI 的职责

### 普通人造人：有自主性的规则 AI

普通人造人使用规则系统，而不是逐人调用大模型。

行为由需求、收益、风险、技能、关系、制度和性格共同决定。居民能够寻找工作、参与项目、获取物资、避险、迁移和支持某个政治势力。

先保证基本行为可靠：不会因任务冲突永久卡住，不会重复占用同一资源，不会无意义地反复换任务，也能在道路被破坏后重新寻找办法。

性格在可靠的执行能力之上影响选择。例如谨慎者更早撤离，利他者更愿意救援，野心者更重视报酬与地位。

### 魔法少女：程序负责能力，决策模型负责人格化取舍

魔法少女的 AI 由本地逻辑与 Jev 类决策模型共同组成，不能把整个世界状态直接交给模型自由发挥。

基本流程为：

**获取她能够知道的情报 → 程序生成可行方案并计算关键条件 → Jev 根据源动力、性格与经历选择 → 本地执行器落实 → 检查结果并更新计划。**

资源计算、路线耗时、危险倒计时、权限和可执行性由程序保证。Jev 主要判断“她重视什么、愿意承担什么代价、在冲突目标之间如何取舍”。

源动力与个人性格应当分开。同样象征希望的魔法少女，也可以分别表现为谨慎务实和鲁莽理想主义。

人格必须影响实际目标、政策、投资、外交和战争选择，而不只是改变台词。允许角色因为自身价值观作出高风险甚至有害的决定，但不应把基础计算错误包装成人格。

Jev 类决策模型主要用于其作为‘官员’时的决策，也就是低频的战略判断；当魔法少女作为在地图上实际存在的个体行动时，移动、战斗操作和日常执行由本地逻辑完成。系统应支持调用预算、响应过期检查、网络故障兜底和决策回放。

## 六、治理、经济与文明演变

### 规划不等于直接操控

魔法少女具有类似 RimWorld 玩家的一部分规划权限，可以提出建筑项目、发展方向、预算、政策和军事目标，但不能直接控制每个普通居民。

居民通过需求满足与拒绝惩罚等机制响应这些规划，可能积极进行，可能优先满足自身需求，也可能拒绝、逃避或离开。

最高统治者可以任命、授权和安排其他魔法少女，但服从不是绝对的。地方实力、利益、关系和价值冲突应影响她们的行为。

### 各系统围绕共同的因果关系运转

生态决定资源条件；居民采集、生产和运输资源；资源支持人口、建筑、科技与战争；这些活动又反过来改变环境与社会。

经济首先应具有可靠的物质账本和物流。同一份资源不能重复存在，国家仓库拥有粮食，也不等于每个居民都能吃到。

科技应解锁新的能力和发展方式，例如储存、灌溉、运输、生产、医疗和装备，重点是地图上可观察到的建筑生产线，而不只是大量百分比加成。掌握知识、拥有设施和获得原料是不同条件。初始科技是蛮族水平，最终科技目前只需要做到中世纪。

战争需要受到实际的用于战斗的士兵的战斗能力限制，包括其装备情况，健康情况，需求情况，以及实际在体素模拟战斗系统下的战斗发挥。标题为战斗类型的魔法少女（例如‘勇气’）可以拥有强大的局部战力，但不能让标题为发展类型的（例如‘美食’）的魔法少女的整个文明的生产与组织失去意义。

叛乱、分裂和篡夺应尽量从不满、利益、支持者、地方实力及危机中产生，而不是纯粹按时间随机触发。

国家的身份、统治者和文化需要分别保存。更换统治者可以改变文明名称，但不应立即抹去原有居民、产业、制度和历史。

## 七、玩家体验：既能干涉，也能看懂

玩家作为管理员，拥有自由干涉世界的能力，包括创造和移除物质、改变环境、制造灾害、影响居民与魔法少女，以及调整世界运行。

管理员可以拥有超出文明规则的权限，但干涉应留下记录，并通过共同的世界系统产生后果，而不只是播放特效。

观察是核心玩法的一部分。玩家应能了解某个居民正在做什么、某位魔法少女为什么选择某个方案、一个国家为何缺粮，以及一次干涉如何导致后续变化。

**理想体验不是只看见“国家灭亡了”，而是能够追溯：大量的灾难性影响（比如在全世界丢下陨石）或滥用加强（无休止地提供食物），又或者是极大偏颇地倾向于某个文明，究竟通过什么样的因果链条，导致了哪些文明的崛起兴衰。**

## 八、技术与开发原则

总体架构采用 **Godot 表现层、独立模拟内核、数据化规则与内容**。

Godot 主要负责显示、界面、相机、声音和交互。高负载模拟优先考虑 C++，界面与流程连接可使用 GDScript。世界状态不能依赖画面或场景节点才能存在，应支持无画面的自动运行与测试。

从早期就建立固定种子、存档、事件日志、AI 决策记录和可复现场景。不能只凭随机种子假定云端 AI 与全部物理结果都能完全重现。

Claude Code 的工作应按小型、可验收的任务推进：实现功能，运行测试，检查真实游戏表现，再继续扩展。不要同时铺开所有系统，也不要用模拟输出冒充实际运行结果。

多人格、多代理或并行开发，都必须服从统一的数据结构、世界时钟、资源规则和存档协议。

## 九、第一阶段的目标

长期目标是一片巨大的、自主发展的空岛大陆，但第一阶段不以地图最大或内容最多为目标。

先建立一个规模受控的完整原型：约一个政权、三位魔法少女、12—24 名普通人造人，以及少量相互关联的生态、资源、建筑和科技。具体规模允许根据性能测试调整。

这个原型必须同时验证地格的生成、休眠、恢复和跨格影响，并打通以下体验：

**玩家破坏水源或运输节点 → 生产与物流受影响 → 魔法少女提出不同应对 → 居民作出不同响应 → 政治支持发生变化 → 文明恢复、衰落或分裂。**

结局不能预先写死。

**《Code:Icarus》的首要成功标准，是让玩家看到：同一个物质世界，因为不同人格的选择与自己的干涉，产生了不同、合理、值得追踪的历史。巨大地图与丰富内容，应建立在这条体验成立之后。**

## 补充需求（开发过程中提出）

- 制作实际游戏的前端 UI 时，从一开始就将美观且利于使用、信息密度合理的 UI 界面设计纳入考量，而不要纯粹地使用朴素的原生 Godot UI。不要使用大量的侧边栏。
